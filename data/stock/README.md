# สต็อกสินค้า — คลังประวัติ

**ไฟล์ในโฟลเดอร์นี้ไม่ใช่ตัวเลขที่ระบบใช้ทำงาน** ตัวเลขสดอยู่ใน Durable Object
ที่นี่คือสำเนาที่ระบบ commit ให้เองทุกคืน 23:55 เวลาไทย เพื่อสองเรื่อง

1. **ประวัติที่อ่านได้** — `git log` ของโฟลเดอร์นี้บอกได้ว่าวันไหนอะไรขยับ ใครยิง
2. **กู้ระบบได้จริง** — ถ้า Durable Object เสียหายทั้งก้อน สร้างใหม่จากไฟล์พวกนี้ได้

เหตุผลที่สต็อกไม่ได้อยู่ในรีโปแบบสด ๆ อ่านได้ที่ [STOCK.md](../../STOCK.md)
สรุปสั้น ๆ คือหนึ่ง commit ต่อการยิงหนึ่งครั้งช้าเกินไปสำหรับงานคลัง และสองคนยิงพร้อมกันจะชนกันตลอด

## ไฟล์อะไรอยู่ที่ไหน

```
data/stock/
├── products.json            ทะเบียนสินค้าและบาร์โค้ด — เขียนเฉพาะเมื่อเปลี่ยน
├── balance/YYYY-MM-DD.json  ยอดคงเหลือปิดวัน แยกตาม SKU และคลัง
└── movements/YYYY-MM.json   การเคลื่อนไหวทั้งเดือน ต่อท้ายทุกคืน ไม่ลบ ไม่แก้
```

### products.json

```json
{
  "products": [
    { "sku": "MTL-30", "name": "เมนทอล 30ml", "unit": "ขวด", "category": "",
      "reorderPoint": 30, "active": 1, "createdAt": "…", "updatedAt": "" }
  ],
  "barcodes": [
    { "barcode": "8851111000012", "sku": "MTL-30", "packQty": 12, "label": "ลัง 12" }
  ],
  "updatedAt": "2026-09-15"
}
```

`packQty` คือยิงบาร์โค้ดนี้หนึ่งครั้งได้กี่หน่วย — ยิงลังได้ 12 ก็ใส่ 12

### balance/YYYY-MM-DD.json

```json
{
  "date": "2026-09-15",
  "version": 1284,
  "balance": [
    { "sku": "MTL-30", "locationId": "main", "onHand": 48, "reserved": 6 },
    { "sku": "MTL-30", "locationId": "damaged", "onHand": 2, "reserved": 0 }
  ],
  "reservations": [
    { "id": "rs_…", "sku": "MTL-30", "qty": 3, "pickedQty": 0,
      "orderRef": "KRY-88214", "status": "open",
      "expiresAt": "2026-09-16T07:02:11.004Z", "createdBy": "sunee" }
  ]
}
```

เก็บเฉพาะการจองที่ยัง `open` เพราะเป็นสิ่งเดียวที่กู้ระบบแล้วต้องไม่หาย
การจองที่แพ็คไปแล้วอยู่ในตาราง movements อยู่แล้ว

**พร้อมขาย** ไม่ได้เก็บไว้ในไฟล์ เพราะคิดได้จาก `onHand − reserved` ของคลังที่ขายได้เท่านั้น
ของในคลัง `damaged` ไม่ถูกนับเป็นพร้อมขายเลย

### movements/YYYY-MM.json

```json
{
  "month": "2026-09",
  "movements": [
    { "id": "mv_…", "ts": "2026-09-15T07:32:04.512Z",
      "sku": "MTL-30", "locationId": "main", "qty": -2,
      "type": "issue", "reason": "", "refType": "order", "refId": "KRY-88213",
      "userId": "malee", "device": "มือถือ" }
  ]
}
```

`qty` บวกคือเข้า ลบคือออก · `type` เป็น `receive` `issue` `return_in` `adjust` `transfer` `count`

`reason` ใส่เฉพาะตอนรับคืนและตอนปรับยอด · ค่าที่ใช้คือ `refused` `box_damaged` `damaged` `other`
และ**เหตุผลเป็นตัวกำหนด `locationId`** ไม่ใช่คนยิงเลือก · `note` คือหมายเหตุที่พิมพ์เอง

`costPerUnit` ใส่เฉพาะ `type: "receive"` และเป็น `null` จนกว่าหัวหน้าจะใส่ต้นทุนจากบิลตัวจริง
ต้นทุนถัวเฉลี่ยใน `products.costAvg` คิดใหม่ทั้งเส้นจากคอลัมน์นี้ตามลำดับเวลาเสมอ
จึงกู้มูลค่าสต็อกจากไฟล์พวกนี้ได้โดยไม่ต้องเชื่อค่าที่แช่ไว้

**นี่คือความจริงตัวจริงของระบบ** ยอดคงเหลือคิดจากผลรวมของตารางนี้ได้ตลอด
ถ้าตัวเลขที่ใช้อยู่ดูไม่ตรง เจ้าของกดปุ่ม "สร้างยอดใหม่จากประวัติ" ได้ทุกเมื่อ

## แก้ด้วยมือได้ไหม

**ไม่ควร** แก้ไฟล์ที่นี่ไม่ทำให้ตัวเลขที่ระบบใช้เปลี่ยน เพราะความจริงอยู่ใน Durable Object
ถ้าต้องแก้ยอดให้ใช้หน้าจอ แล้วคืนนั้นสำเนาจะตามมาเอง
